# 案例：「同步」這個詞讓使用者搞不清楚按鈕會做什麼

> 一個 UI 詞彙混用的問題，以及怎麼跟 Claude 一起把它拆解清楚的紀錄。

## 背景

PodcastRAG 是一個讓使用者選 Podcast 節目、用 RAG 對逐字稿做語意查詢的小型專案。後台的「排程管理」分頁裡有幾顆按鈕，使用者可以為每個節目設定自動轉錄、手動觸發、或批次操作。

第一版做完並部署上線後，自己手動測試時發現 UX 跟預期不一致 —— 但具體是哪裡不對，當下說不清。

## 一開始模糊的不滿

最初記下來的議題只有三條：

1. 「同步所有」按鈕點下去後，被關掉的 toggle 應該被自動切回開啟？
2. 「排程」設定的時間頻率好像沒有真的在跑？
3. enable toggle 到底擋住了什麼？

這三條看起來是三個獨立功能點，但其實**根因是同一個**：UI 上「同步」這個詞被同時用在兩件性質完全不同的事情上。

## 跟 Claude 討論時的關鍵轉折

進到 `/spectra-discuss` 後，Claude 用 Assumptions 模式列了 4 個假設請我挑錯。但我看完之後反問了一句：

> 「目前的同步，這件事會去執行什麼動作？是開始執行轉錄排程嗎？我這邊有點困擾。」

這句話讓討論直接跳到根因。Claude 去翻了 backend 程式碼，把所有相關按鈕的**真實行為**列出來：

| 按鈕 | endpoint | 實際做的事 |
|------|----------|-----------|
| 「同步集數」 | `/shows/{id}/sync` | 只抓 RSS upsert 集數清單 |
| 「立刻執行」 | `/shows/{id}/transcribe-latest` | 抓 RSS + 排隊轉錄 |
| 「同步所有」 | 對每個 enabled 節目跑 transcribe-latest | 抓 RSS + 排隊轉錄（會燒 OpenAI quota） |

問題立刻清楚了：

```
       ┌─────────────────┐         ┌──────────────────┐
       │   抓 RSS 更新    │         │  排隊轉錄         │
       │   集數清單       │         │ （燒 API quota） │
       └─────────────────┘         └──────────────────┘
              ▲                              ▲
              │                              │
       ┌──────┴────────┐              ┌──────┴────────┐
       │ 「同步集數」    │              │ 「立刻執行」    │
       └───────────────┘              └───────────────┘
                                             ▲
                                             │（每個 enabled 節目跑一次）
                                      ┌──────┴────────┐
                                      │ 「同步所有」    │ ← 名字騙人
                                      └───────────────┘
```

**真正的兩個動詞是「更新清單」和「轉錄」**。「同步」這個字被同時掛在兩邊，所以亂。「同步所有」字面像輕量操作，實際會燒錢。

## 解決方案

### 1. 詞彙：把「同步」從 UI 完全砍掉

| 原名 | 新名 | 行為 |
|------|------|------|
| 同步集數 | **更新節目集數** | 只抓 RSS |
| 立刻執行 | 立刻執行（保留） | 抓 RSS + 轉錄 |
| 同步所有 | **轉錄未完成集數**（批次） | 抓 RSS + 轉錄 |

### 2. 互動模型：改成 Gmail 風的 checkbox + 批次按鈕

原本的 toggle 試圖同時表達兩件事：「這個節目要不要被批次操作包含」和「這個節目要不要自動跑」—— 兩個維度被壓在同一個 UI 上。

新設計：

- **動作層**：每列一個 checkbox，勾選後頂端出現批次按鈕（更新節目集數 / 轉錄未完成集數）
- **狀態層**：原本的 enable toggle 改名「自動轉錄」，移到「編輯排程」modal 裡（給未來 cron 用，現在沒 cron 所以標示「待功能上線」）

這樣 checkbox 是「現在做」、toggle 是「未來自動做」，兩個維度天然分開。

### 3. 安全網

批次轉錄會燒 quota，因此跳一次 confirm：「即將對 N 個節目排入轉錄」。單次操作不擋。

## 從這個案例學到什麼

1. **使用者最初描述的問題不一定是真問題。** 一開始列了三條議題，看起來像三個功能點要修。但真正的根因是「同步」這個詞混用，修詞彙就同時解掉三條議題。

2. **「困擾」這種模糊感受，是值得認真追的訊號。** 不要急著回答 yes/no 題，先問「現在實際在做什麼？」把行為攤開，意義往往就浮出來了。

3. **狀態 vs 動作要在 UI 上分得清楚。** toggle 是 persistent state，按鈕是 transient action。把兩者混在一個 widget 裡（例如「toggle 影響某個批次按鈕的範圍」）幾乎一定會讓人搞不清楚。

4. **詞彙是 UX 的一部分。** 「同步」這個詞在工程師眼中很自然，但它對使用者來說沒指明「同步什麼」「同步到哪」「會不會花錢」。換成「更新集數」「轉錄」這種**動詞 + 受詞**結構，使用者一看就知道後果。

5. **跟 AI 討論時，反問比照單全收更有價值。** Claude 列了一份合理的假設清單，但真正讓討論收斂的是一句反問「同步到底在做什麼」。AI 給的結構是工具，不是答案。

## 後續

這個結論被開成一個 Spectra change proposal 進入正式流程實作。記錄的目的是讓之後類似情境（UI 詞彙混用、使用者說不清哪裡不對）有一個可參考的拆解步驟。
